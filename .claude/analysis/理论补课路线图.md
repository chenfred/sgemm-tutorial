# 理论补课路线图：看懂 ncu、自己找到 SGEMM 优化方向

这份文档基于本次 `naive vs v1` 的实测分析，反推出**要补哪些理论知识**才能看懂报告、并独立判断下一步优化方向。每条都标注「在本次分析里体现为」和「学完能回答什么」。

建议学习顺序 = 下面 A→G 的顺序（地基 → 存储 → 占用率 → 延迟 → 模型 → 手法 → 终极）。

---

## A. GPU 执行与指令发射模型（地基）

**概念**：SIMT、warp、SM、SM Partition（SMP）/warp scheduler、issue slot、IPC、`blockDim`/`gridDim` 的硬件映射。

**关键事实（Blackwell sm_120）**：
- 1 个 SM = 4 个 SMP，每个 SMP **1 个 warp 调度器**，每周期每调度器**最多发 1 条 warp 指令**（同一 warp 同周期不能双发）。
- 整 SM 每周期最多 4 条 warp 指令（**来自不同 warp**）。
- 本机：CC 12.0、**84 个 SM**；1 个 SM = **4 个 SMSP（sub-core）**，每 SMSP **1 个 warp 调度器 + 32 个 FP32 core**（整 SM 共 128 FP32），一条 `FFMA`（32 线程）在该 SMSP 的 32 个 FP32 上 **1 周期**并行完成；每 SMSP 跟踪 12 warp → **48 warp/SM**（与实测 Theoretical 48 吻合；Blackwell 是 48，非 Ampere/Hopper 的 64）。SMSP 可粗略看作 4 个小核，但**共享**寄存器文件与 128KB L1/shared。

**本次体现**：Compute Workload 里的 `Issued Ipc Active`（naive 1.13 / v1 1.71）、`Issue Slots Busy`。

**学完能回答**：为什么 IPC 不是 32？为什么「同周期多发射无依赖指令」在 Blackwell 上不成立？→ 见主报告 Q3 与上次讨论。

**资料**：
- NVIDIA 《CUDA C++ Programming Guide》→ *Hardware Implementation*。
- [Dissecting the NVIDIA Blackwell Architecture (arXiv 2507.10789)](https://arxiv.org/html/2507.10789v1)。

---

## B. 存储层次与带宽（性能主战场）

**概念**：register → **L1/TEX cache（shared memory 也走这条 pipe）** → L2 cache → DRAM（global memory）。各级容量、带宽、延迟的数量级差异。

**关键事实**：
- **shared memory 和 L1 cache 共享同一条 pipe**（L1/TEX），所以 `L1/TEX Cache Throughput` 饱和 = 这条 pipe 被打满，不论流量来自 shared 还是 global。
- **coalescing**：以 32B sector 为单位合并访问；warp 内 32 线程访问连续地址 = 1 个 128B 事务（4 sector）。
- Blackwell **sm_120**（GB203/RTX 50）每 SM 有 **128KB 统一 L1/shared memory**（按需在 L1 cache 与 shared 之间 carve-out；本报告默认 carve 出 ~64KB 给 shared，故 `Shared Memory Configuration Size` 显示 65.55KB）。对比：Hopper sm_90 = 256KB、Blackwell 数据中心 sm_100 = 228KB、消费级 sm_120 缩到 **128KB**。

**本次体现**：`L1/TEX Cache Throughput 97%`（naive）就是 shared memory 访问打满了这条 pipe —— 这是 naive 真正的瓶颈，也是两者共同的墙（主报告 Q4）。

**学完能回答**：为什么 shared memory 访问会成为瓶颈？为什么 DRAM 才 7% 也很慢？怎么降低 L1/TEX 压力？

**资料**：《Best Practices Guide》→ *Memory Optimizations*；Simon Boehm 矩阵乘博客讲 coalescing 很直观。

## C. Occupancy（占用率）—— 本次的次要主因

**概念**：active warps / max warps per SM。分 **Theoretical**（资源允许的上限）和 **Achieved**（实际）。

**怎么算**：每 SM 可驻留的 block 数 = `min(Block Limit Warps, Registers, Shared Mem, Barriers)`。其中：
- `Block Limit Registers = floor(64K / (regs_per_thread × threads_per_block))`
- 最终 block 数 × 每 block 的 warp 数 = active warps/SM。

**关键洞察**：占用率由「**最先顶住的那一项**」决定。寄存器用多了 → 占用率掉 → 能藏延迟的 warp 变少。

**本次体现**：v1 `Registers=55` → `Block Limit Registers=4` → 占用率 66.7%（naive 100%）。直接对应 GUI Occupancy 柱状图里 Registers 那根最矮的柱。

**学完能回答**：为什么多用了几个寄存器，占用率就掉 1/3？占用率和性能是不是线性关系？（不是，有递减回报，且对 compute-bound kernel 不总是关键。）

**资料**：《Programming Guide》→ *Maximize Memory and Arithmetic Throughput / Occupancy*；CUDA Occupancy Calculator（现在集成在 ncu 里）。

---

## D. Warp Stall 与延迟隐藏（TLP vs ILP）—— 本次最易搞错的地方

**概念**：GPU 不像 CPU 靠乱序多发射藏延迟，而是靠**多 warp 轮转（TLP）**；同一 warp 内多条无依赖指令（ILP）是次要补充。两者近似**乘积关系**：能否喂饱流水线 ≈ `active warps × ILP per warp`。

**Stall 原因分类**（见 `如何阅读ncu-rep.md` 第 4 节表）：`Long/Short Scoreboard`（等内存/寄存器）、`Wait/Barrier`（同步）、`Not Selected`（无碍）、`* Throttle`（单元限流）等。

**关键纠错**：单 warp ILP=1 不必然慢 —— 只要占用率够、有别的 ready warp 顶上。本次 naive ILP=1 但靠 98.7% 占用率藏住了。

**本次体现**：`Warp Cycles Per Issued Instruction`（naive 42 / v1 18.2）、`No Eligible`（naive 71.8% / v1 57.5%）。我初版误判「ILP=1 是首要嫌疑」，实测 IPC 1.71 推翻了它。

**学完能回答**：看到 `No Eligible` 高该怎么改？什么时候加 ILP（多累加器）有用、什么时候提占用率有用？

**资料**：[How does ILP and TLP work on GPUs? (SO)](https://stackoverflow.com/questions/18068264/)、[Understanding Latency Hiding on GPUs (Berkeley EECS)](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2016/Archive/EECS-2016-143.pdf)。

## E. Speed-of-Light（SOL）与 Roofline（分析方法论）

**概念**：
- **SOL**：把每个子系统的实际吞吐除以它的峰值，得到「离天花板多远」。谁最接近 100% 谁就是瓶颈。
- **Roofline**：以「算术强度（FLOP/Byte）」为横轴、「可达吞吐」为纵轴，画出 compute 屋顶和 memory 屋顶的交点，判断一个 kernel 是 compute-bound 还是 memory-bound。

**本次体现**：SOL 是整份报告的入口（Compute 92% / Memory 92% / L1/TEX 97%）。两者都已撞墙。

**学完能回答**：拿到一个新 kernel 的 ncu，怎么 30 秒内判断它是 compute-bound 还是 memory-bound？该往算力还是带宽方向优化？

**资料**：Nsight Compute 官方文档 *Speed Of Light*；经典 Roofline 论文（Williams et al., CACM 2009）。

## F. Kernel 优化手法（连接理论与代码）

这是把上面知识**变现**成代码的部分。SGEMM 从 naive 到高性能的标准进阶：

1. **Shared memory tiling**（naive 已有）：用 shared memory 复用 A/B 子块，降低 global 流量。
2. **Register tiling**（v1 尝试，但粒度太小）：让每个线程算多个 C 元素、累加器放寄存器，**核心目的是减少 shared memory 访问次数**（每次 shared load 喂更多 FMA）。本次实测显示 L1/TEX 97% 饱和，正是要靠这一步缓解。
3. **向量化加载**（`float2/float4`）：减少加载指令数、提高 coalescing —— 直接对应 v1「指令多 62%」的痛点。
4. **1D thread mapping**：用 `tid = ty*blockDim.x+tx` 线性编号 + 整除定位，避免 v1 那种重排导致的复杂索引。
5. **Double buffering / 软件流水线**：用两份 shared buffer，加载与计算重叠，隐藏 `__syncthreads` 等待 —— 直接对应 v1 `KS=8` 的 sync 开销。
6. **`#pragma unroll`**：让编译器展开内层循环、更好的指令调度与寄存器分配。

**本次体现**：v1 栽在 (2) 粒度太小、(3)/(4) 缺失导致指令爆炸、(6) 没加。v2 应沿这几条改。

**资料**（按顺序读，非常经典）：
- **Simon Boehm — Matrix Multiplication on GPU**（从 0 到 ~1 TFLOPS 逐版优化，最推荐入门）。
- **Lei Mao — How to Optimize a CUDA Matmul Kernel**（register tiling 讲得细）。
- **NVIDIA CUTLASS** 源码与文档（生产级实现范本）。

## G. Tensor Core（真正的下一步）

**概念**：FP32 CUDA core 的 GEMM 天花板就几个 TFLOPS（本次 ~4.5 TFLOPS 已近墙）。要再上一个数量级，得用 **Tensor Core**，通过 `wmma`（CUDA C++ 封装）或 `mma`（PTX）做矩阵分块乘（如 16×16×16）。

**本次体现**：两者 GFLOPS 都不高、SOL 都撞墙 → 说明纯 CUDA core 路线已接近尽头，下一步该评估是否切到 Tensor Core。

**学完能回答**：什么时候该放弃 CUDA core、上 Tensor Core？`wmma` 怎么改写当前 kernel？

**资料**：《Programming Guide》→ *Warp Matrix Functions*；NVIDIA `cuda-samples` 的 `TensorOp` 示例；CUTLASS 的 DDOC/`gemm` 教程。

## 一页速查：看 ncu 的决策树

```
1. Speed of Light: Compute vs Memory 谁高？
   ├─ Memory 高 → 看 DRAM/L1-TEX/L2 哪级饱和
   │   ├─ L1/TEX 高 → shared memory 访问压力（本次！）→ 放大 register tile / 减少访问
   │   └─ DRAM 高 → 访存太多 → tiling / coalescing / 向量化
   └─ Compute 高 → 算力受限 → 看是不是该上 Tensor Core

2. Warp State: 最大的 stall 原因是什么？
   ├─ Long/Short Scoreboard → 访存/寄存器依赖（配合第 1 步）
   ├─ Wait/Barrier → 同步过多 → 放大 K-tile / double buffer
   └─ Not Selected → 占用率够、无碍

3. Occupancy: Block Limit 哪项最小？
   ├─ Registers → 降寄存器（本次 v1！）或接受低占用率换更强 ILP
   ├─ Shared → 减 shared 或提 block 数
   └─ Warps → 调 block size

4. Instruction/Source: 指令数是否异常多？热点在哪几行？
   └─ 多余的整数/地址指令（本次 v1 +62%）→ 简化索引、向量化
```
