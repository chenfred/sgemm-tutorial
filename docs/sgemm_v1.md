# v1：一个线程算同一列上的四个输出

[源码](../src/sgemm_v1.cu) · [上一版 v0](sgemm_v0.md) · [下一版 v2](sgemm_v2.md)

v1 把 C 块扩大到 32×32，但仍只用 256 个线程。多出来的输出由每个线程负责四个来解决。

## 谁算哪些位置

仍然是行存储的 `C(M,N)=A(M,K)×B(K,N)`。

| 项目 | 当前配置 |
|---|---|
| block | x=32、y=8，共 256 个线程 |
| C tile | 32×32 |
| K tile | 32 |
| 每线程输出 | 4 行 × 1 列 |
| shared | A、B 各 32×32，共 8 KiB |

block 起点为 `baseRow=blockIdx.y*32`、`baseCol=blockIdx.x*32`。grid 按 N 的列、M 的行分别向上取整。

线程 `(tx,ty)` 负责：

```text
C[baseRow + ty     ][baseCol + tx]
C[baseRow + ty +  8][baseCol + tx]
C[baseRow + ty + 16][baseCol + tx]
C[baseRow + ty + 24][baseCol + tx]
```

注意这四行相隔 8，不是相邻四行。例如线程 (3,2) 算块内第 3 列、第 2/10/18/26 行。四个结果分别存在 `regs[0..3]`。

## 数据怎么搬、怎么算

每轮处理 32 个 K 位置。一个线程把 A、B 各搬四个元素：循环 `ii=0..3`，负责 shared 中第 `ty+8*ii` 行、第 tx 列。

这里 B 的 shared 行代表 K，A 的 shared 行代表 M；两者虽然使用同一个 `tileRow`，在原矩阵里的含义不同。一个 warp 的 tx 从 0 到 31，A 沿 K 连续访问，B 沿 N 连续访问。

搬完后 barrier，然后为四个输出各做一段长度为 32 的点积：

```cpp
for (ii = 0; ii < 4; ++ii) {
    for (t = 0; t < 32; ++t) {
        regs[ii] += tileA[ty + 8*ii][t] * tileB[t][tx];
    }
}
```

计算后再 barrier，防止下一轮覆盖仍有人在读的 shared。全部 K 块完成后，四个累加器分别写回。

## 比 v0 多学了什么

同一个线程的四个输出使用同一段 B 列数据，因此存在 B 数据复用的机会；一个线程还有四条独立累加链，可给指令调度更多空间。

但源码仍然是 ii 在外、t 在内，并没有显式写“先读一次 B，再更新四个结果”。实际能复用多少、如何调度，取决于编译器生成的指令。不要只数源码中数组出现了几次就当成实际访存次数。

边界策略与 v0 相同：A 检查 M/K，B 检查 K/N，越界补零；四个输出逐个检查 M/N。shared 扩大、每线程工作增加都带来成本，所以不是把 `OUTPUTS_PER_THREAD` 一直加大就会一直快。

回来时先记住：256 个线程算 1024 个输出，靠的是每线程四个累加器。下一版把“一列四个”扩展成二维输出分工。
