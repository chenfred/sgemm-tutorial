# v2：每线程算 12×3 个输出

[源码](../src/sgemm_v2.cu) · [上一版 v1](sgemm_v1.md) · [下一版 v3](sgemm_v3.md)

v2 让线程同时负责多个输出行和多个输出列。每个 K 位置先读出 12 个 A 和 3 个 B，再用它们更新 36 个结果。

## 三层分工

矩阵仍为行存储的 `C(M,N)=A(M,K)×B(K,N)`。

| 层次 | 当前大小 |
|---|---|
| block 的线程排列 | x=32、y=8，共 256 个 |
| block 的 C tile | 96 行 × 96 列 |
| K tile | 32 |
| 每线程累加器 | 12 行 × 3 列，共 36 个 float |
| shared A | 96×32 |
| shared B | 32×96 |
| shared 合计 | 24 KiB |

`TILEBASE_X/Y=32/8` 是线程排列；`REG_TILE_X/Y=3/12` 是每线程输出数量。两者相乘才得到 C tile 的 96×96。

grid 是 `(ceil(N/96), ceil(M/96))`。线程 (tx,ty) 负责的块内坐标为：

```text
行：ty, ty+8, ty+16, ... , ty+88
列：tx, tx+32, tx+64
```

这些行列交叉得到 36 个输出。比如线程 (0,0) 算第 0/8/.../88 行与第 0/32/64 列的交叉点。所谓“12×3 register tile”是逻辑分工，不是 C 中连续的一个小矩形。

## 每轮如何装满 shared

A 的 96×32 块：每线程搬 12 个元素，块内位置为 `[ty+8*ri][tx]`。

B 的 32×96 块：每线程搬 4×3=12 个元素，块内位置为 `[ty+8*bi][tx+32*rj]`。

因此 A/B 各有 `256*12=3072` 个元素，刚好填满。相邻 tx 对应连续地址：A 沿 K、B 沿 N。搬运职责和输出职责不要混淆，B 的四行来自 K tile 的 32 行除以 block.y 的 8。

代码把 K tile 单独写为 `TILE_K`，但仍要求它是线程排列两个轴的整数倍，方便每线程均匀分工。当前固定为 32，不需要为读懂代码去调参数。

## 计算：15 个输入更新 36 个结果

搬完 shared 并同步后，对块内每个 k：

```text
读取 12 个 A → regA[12]
读取  3 个 B → regB[3]

对所有 ri、rj：
    regs[ri][rj] += regA[ri] * regB[rj]
```

一个 A 值参与三个输出，一个 B 值参与十二个输出。这就是这里说的“外积”：一组列方向的 A 值和一组行方向的 B 值两两相乘，更新一个逻辑上的二维输出块。仍然是普通 FP32 乘加，没有用 Tensor Core。

每个 K tile 有 32 次上述更新。累加器跨所有 K tile 保留，最后一次性写回 C。

## 两个 barrier 为什么还在

第一个保证大家搬完，才能跨线程读 shared；第二个保证大家读完，才能覆盖它。此版只有一套 shared，所以源码按“搬一块、算一块”反复执行，没有 v3 那样显式安排 next 预取。

尾块的 A 检查 M/K、B 检查 K/N，越界写零；输出按 M/N 判断。即使不是 96 或 32 的整数倍，也使用相同的整块计算。

比 v1 多的是明确的二维寄存器复用，同时代价是更多累加器和更大的 shared。36 个累加器不等于总共只用 36 个寄存器，地址、输入和临时值也要占位置。

重读时按“常量 → 搬 A/B → k 外层计算 → 写回”看一遍即可。v3 保留这套分工，开始调整搬运和计算的先后次序。
